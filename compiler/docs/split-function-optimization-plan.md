## Implementation sequence

1. Inspect helper calls, tuple return marshalling, route dispatch, globals, and local setup.
   Check the actual splitter ABI and identify reproducible correctness failures or unnecessary
   emitted work before changing a lowering.
2. Improve switch lowering. The compiler currently emits a JVM `tableswitch` for every Wasm
   `br_table`, including sparse tables. Select the smaller JVM encoding using actual target
   entries, omit lookup entries that equal the default, and handle a table with no explicit
   entries. Preserve signed JVM selector handling for Wasm's unsigned out-of-range selectors
   and backward-edge interruption checks.
3. Investigate forwarding a helper call's multivalue result when the caller immediately returns
   it. Remove unpack/repack work only when result types and control flow permit it. Preserve
   ordinary call exception handling and the existing Wasm tail-call trampoline semantics.
4. Add cohesive regression coverage: compiler/interpreter agreement, boundary selectors,
   mixed return types, exceptional paths, and structural checks on generated JVM bytecode.
   Include input/output from the actual Binaryen splitting pass where practical.
5. Run focused tests, then compiler and relevant specification suites plus formatting/static
   checks. Record exact generated-code changes and reproducible local diagnostics. Runtime
   speedup claims require measured evidence; local checks do not establish fixed-runner thesis
   acceptance.

## Acceptance

- No change to exported values, traps, ordinary exception handling, or interruption behavior.
- Sparse and empty `br_table` modules compile and execute correctly; emitted dispatch uses the
  smaller representation without inflating dense tables.
- Accept call/return forwarding only with correctness and performance evidence. Retain normal
  marshalling if the experiment does not establish a useful improvement.
- Existing focused and broader compiler checks pass, with any unrelated failures stated.
- Results and remaining opportunities are appended below after implementation.

## Deferred investigations

Typed tuple carriers, cached mutable mailbox globals, and skipping local initialization need
separate ABI, reentrancy, or definite-assignment designs. Do not introduce them without evidence
and suitable correctness coverage in this change.

## Implementation findings

- Added `SwitchEmitter`: retain dense `tableswitch` encodings, omit default-equivalent lookup
  keys, and optionally use the most common target as the lookup default behind explicit bounds
  checks for tables of at least 8,000 encoded bytes. Local small-table timings did not justify
  adding those guards to smaller tables. A conservative size comparison accounts for the checks.
  Empty and default-only tables become a pop and jump. Existing backward-edge checks stay in the compiler.
- Prototyped ordinary `CALL_RETURN` forwarding for adjacent, exactly matching multivalue calls.
  Correctness tests passed, but timing varied between trials and allocation stayed unchanged.
  The prototype was removed from the final implementation. Normal result marshalling remains;
  future forwarding work needs evidence from real split helpers and their JVM compilation.
- Reproduced an additional compilation bug: a valid `i32` plus 128 `i64` result tuple tries to
  invoke a 257-slot `value_xxx` method and throws `IllegalArgumentException: bad parameter count
  257`. Results exceeding the JVM's 255 parameter-slot limit are now packed inline, with reserved
  scratch slots and both numeric and reference array representations covered by tests.
- Added ten focused regression tests, including generated tuple and mailbox fixtures from the
  custom Binaryen pass. `scripts/regenerate-split-function-fixtures.sh` rebuilds these fixtures
  using the executable's matching `libbinaryen`.
- Added `BenchmarkSplitFunctionBoundaries` for repeatable local allocation/timing diagnostics.
  HotSpot already eliminates intermediate tuple arrays in these synthetic forwarding chains;
  source-level allocation removal is therefore not evidence of a GC or runtime speedup.
